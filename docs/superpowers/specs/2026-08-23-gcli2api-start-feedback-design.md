# gcli2api 启动反馈修复设计

日期：2026-08-23

## 问题

当前“启动服务”只负责创建 gcli2api 进程，成功回调仅在 1.5 秒后静默检测一次。界面不会弹出启动结果，而且进程创建成功不等于 HTTP 服务已经可用，用户无法判断下一步该做什么。

## 目标

- 点击“启动服务”后等待本地服务真正响应，最长等待 15 秒。
- 服务可以调用时，明确提示“服务已启动”，显示地址和模型数量。
- 服务已运行但尚无模型时，明确提示服务已启动，并引导用户打开面板、使用同一密码登录并完成 Google OAuth。
- 服务已经运行但 API 密码不匹配时，不重复创建进程，提示用户检查密码。
- 进程提前退出、端口无法响应或等待超时时，显示具体失败原因，不能误报成功。
- 启动结果立即同步到卡片状态；运行中禁用“启动服务”按钮并显示“已启动”。
- 卡片常驻显示与当前状态匹配的分步操作指引，用户不需要依赖记忆弹窗内容。
- 不上传 GitHub，仅生成本地测试版 EXE。

## 设计

`Gcli2ApiManager` 增加可测试的“启动并等待”流程。它先探测现有服务，避免端口上已有实例时重复启动；需要启动时创建进程并轮询 `/v1/models`。任何能够确认 HTTP 服务存在的状态都会被返回给界面，但只有就绪或缺少 OAuth 被视作本次启动成功；密码错误、HTTP 异常、进程退出和超时分别返回可执行的错误说明。

GUI 后台线程调用该流程，避免阻塞窗口。完成后立即渲染返回的状态：成功使用信息弹窗，失败使用错误弹窗。状态按钮根据 `status.running` 切换为“已启动”或“启动服务”。

卡片增加常驻“下一步”指引，并随状态切换：

1. 未安装：点击“一键安装”。
2. 已安装未运行：填写本地 API 密码，然后点击“启动服务”。
3. 服务运行但缺少 OAuth：打开面板，用同一密码登录，完成 Google OAuth，返回软件点击“检测服务”。
4. 服务就绪：选择模型，添加到 Claude，在 API 供应商中“测试并使用”，最后选择项目并快速启动 Claude。
5. 密码或服务异常：显示原因，并明确提示用户修改密码、检查面板或重新检测。

启动成功弹窗重复呈现当前阶段的关键步骤，避免用户关闭弹窗后失去方向。

“本地 API 密码”明确解释为用户自己为本机服务设置的密码，不是 Google API Key，也不需要从第三方申请。未运行时允许用户自己输入，或点击“生成并复制”创建强密码；软件启动服务时将同一个值设置为 `API_PASSWORD` 和面板密码。若服务已从终端启动，则必须填写终端启动时已有的 `API_PASSWORD`，不能重新生成并覆盖。

## 验证

- 单元测试覆盖：已经运行、正常启动并就绪、启动后等待 OAuth、进程提前退出、启动超时以及各状态对应的下一步指引。
- 运行完整 pytest 测试集。
- 使用 PyInstaller 构建单文件 EXE，启动并检查 gcli2api 卡片及启动提示流程。
- 确认远端分支未发生变化。
